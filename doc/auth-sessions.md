# Auth sessions

Conjin initializes the current identity on every request, but starts a PHP session only when needed. Without a session cookie, an ordinary guest visit resolves the guest identity in memory and creates neither a session nor a session cookie. Existing sessions are resumed during `auth_init()` before authorization. Password-cookie and trusted internal authentication can resolve identities without creating a new session.

Framework code starts sessions through `auth_ensure_session_started()` in `src/conjin/inc/auth_session.php`. It is idempotent, verifies that headers are still available, and rejects startup failure. `auth_resume_session_if_present()` resumes an existing cookie-backed session without creating one for a visitor with no session cookie. PHP's configured session name determines the cookie name. Before startup the auth layer disables PHP's automatic session cache limiter; response caching follows the explicit [HTTP cache policy](http-caching.md) instead.

Displaying the password login page and rejecting an incorrect password do not create a session. A successful password login starts a session before persisting the identity. Logout and OIDC handlers ensure a session exists before storing their state. Their existing authentication behavior is retained, including login errors and logout confirmation. The OIDC dependency has its own session methods and may close the session; Conjin reopens it before persisting callback identity or failure state.

Issuing a [submission token](submission-tokens.md) ensures a session exists. Token validation without an existing session rejects the request rather than creating an empty session. Code needing persistent state must ensure the session is active before writing it; do not persist a guest merely to represent the current request's identity.

The request entrypoint starts an outer output buffer before initialization. It remains until response completion, allowing session cookies and cache headers to be sent even when a form requests a token after HTML generation has begun. Normal rendering must not flush this outer buffer early. Redirect and error helpers may discard buffered content when terminating a response. A session request after headers were actually sent raises a descriptive exception identifying where output began. Responses requiring streaming must arrange session use before sending output.

This change does not remove analytics' use of already-active sessions. A module that checks `session_status()` without requesting a session observes only sessions resumed or started earlier in the request.

Successful password and OIDC authentication use `auth_persist_authenticated_user()` to start or reopen the session, regenerate its ID with deletion of the previous session, and only then store the authenticated identity. Existing session data survives rotation, including the OIDC redirect destination. PHP sends the replacement session cookie; the previous ID cannot resume the authenticated session. Rotation failure aborts identity persistence. Failed logins and ordinary session resumption do not rotate the ID.

Before starting or reopening a session, the auth layer enables `session.use_strict_mode` and `session.use_only_cookies`. Session cookies use `HttpOnly`, `SameSite=Lax`, path `/`, no Domain attribute (host-only), and lifetime zero (a browser-session cookie). The existing generated `https` configuration controls `Secure`: local/test deployments and remote `Off` use false; remote `Prefer` and `Force` use true. Authenticated use of a `Prefer` deployment therefore requires HTTPS even though public HTTP access remains possible. Request headers, including forwarded headers, do not influence this policy. No deployment schema change or regeneration is required for these defaults. Failure to apply the settings aborts session startup.

The policy is applied before the OIDC flow starts and again when Conjin reopens a session closed by the OIDC client. `SameSite=Lax` supports the current top-level GET callback flow; an identity provider configured to POST callbacks would need a separately considered cookie policy. Cookie lifetime does not implement an authentication idle or absolute timeout. Custom session save handlers must implement session ID validation for strict mode to work.

## Logout

Logout accepts only POST at `auth_get_logout_url()`. Forms must include an HTML-escaped `logout_token` issued by `auth_issue_submission_token('auth:logout')`. The handler validates and consumes that token before changing the session identity. Other HTTP methods return 405 with `Allow: POST`; missing, invalid, expired, already-used, wrong-identity, wrong-scope or wrong-session tokens return 403 without changing authentication. A successful logout retains the confirmation message and responds with a 303 redirect to the login page. Tokens must stay in form bodies, never URLs; pages containing these forms must not enter a shared cache.

The built-in sidebar and unauthorized-page templates use ordinary POST forms and work without JavaScript. Custom templates must replace logout anchors with equivalent forms; `auth_get_logout_url()` remains the form-action URL. Logout changes only session authentication: it never clears or changes the password authentication cookie. A request carrying a valid password cookie will continue to authenticate on subsequent requests.
